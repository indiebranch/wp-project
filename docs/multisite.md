# Optional private Multisite

This template is single-site by default. A derived project can opt into a privately
managed Multisite network. Network administrators provision sites and users through
Network Admin or WP-CLI; public signup is disabled by the `private-multisite.php`
must-use plugin. No Multisite database conversion happens automatically.

## Choose a network layout

- **Subdirectories:** sites such as `https://example.com/site-one/`. No extra local
  hostnames are required. WordPress may restrict conversion of older installations
  to this layout; check the Network Setup screen.
- **Subdomains:** sites such as `https://site-one.example.com/`. Configure DNS,
  HTTPS certificates, and web-server routing for each hostname. For mapped domains,
  provision those hostnames too.

The examples below assume the network is served at `/`, with core in `/wp` and
shared content in `/app`, as in this template.

## Configure DDEV

Keep `type: wp-bedrock` and `docroot: public` in `.ddev/config.yaml`.
For either layout, copy `.ddev/nginx/multisite.conf.dist` to
`.ddev/nginx/multisite.conf` to enable the Bedrock core/admin rewrites.

For subdomains only, also copy `.ddev/config.multisite.yaml.dist` to
`.ddev/config.multisite.yaml`. Replace `site-one.wp-project` with the hostname
prefix for each subsite. DDEV appends `project_tld`: with the starter defaults,
that example becomes `site-one.wp-project.indiebranch.ddev.site`. If the project
name or TLD changes, adjust the entries accordingly. For unrelated mapped domains,
use DDEV's `additional_fqdns` setting instead.

Run `ddev restart` **on the host** after these changes. Commit the active config
files in the derived project. Production servers need equivalent routing and TLS
configuration; these DDEV examples configure only local development.

## Convert an installed site

1. Back up the database and uploads. On DDEV, run `ddev snapshot` on the host.
2. Add `WP_ALLOW_MULTISITE=true` to the project's `.env`, leaving `MULTISITE`
   unset. Sign in as an administrator and follow **Tools → Network Setup**.
   WordPress may require deactivating plugins during conversion; reactivate the
   appropriate plugins afterwards, network-wide where required.
3. Complete the database/network installation. Translate the constants shown by
   WordPress into `.env` values rather than editing `public/wp-config.php`:

   ```dotenv
   WP_ALLOW_MULTISITE=true
   MULTISITE=true
   SUBDOMAIN_INSTALL=false
   DOMAIN_CURRENT_SITE='wp-project.indiebranch.ddev.site'
   PATH_CURRENT_SITE='/'
   SITE_ID_CURRENT_SITE=1
   BLOG_ID_CURRENT_SITE=1
   ```

   Use `SUBDOMAIN_INSTALL=true` for subdomains. Use your actual network domain
   and the IDs generated by WordPress. `DOMAIN_CURRENT_SITE` has no scheme, port,
   or path. Keep `WP_HOME` set to the main site's public URL: it still supplies
   the shared `/app` content URL. In Multisite, `WP_HOME` and `WP_SITEURL` are not
   defined as WordPress constants, allowing each site's database URLs to work.
4. Use the DDEV rewrites above rather than WordPress's suggested Apache rules.
   Sign in again, then visit **Network Admin → Settings**. Registration should
   show as disabled and site administrators should not be allowed to add users.
   The mu-plugin enforces these effective settings even if stored values differ.
5. Persist the same closed-registration settings in the database:

   ```bash
   ddev wp network meta update 1 registration none
   ddev wp network meta update 1 add_new_users 0
   ```

   Substitute the actual network ID if it is not `1`.
6. Create a test subsite through Network Admin. Verify its homepage, admin area,
   login/logout, media URLs and permalinks. Verify that `/wp/wp-signup.php` does
   not offer public registration. Verify required plugins on the subsite too.

Network-activate Two-Factor to apply the starter's two-factor policy throughout the
network. It requires 2FA for site administrators and super administrators, even
when a super administrator has no role on the current site. For initial enrollment,
temporarily set `ENFORCE_TWO_FACTOR_POLICY=false`, configure a provider for each
administrator, then restore enforcement. Existing 2FA requirements remain in place
while this toggle is disabled.

## Advisory: CVE-2017-14990

WordPress stores Multisite signup activation keys in plaintext. An attacker with
database read access could use a pending signup's key to activate that account.
The Composer advisory exception is an acceptance based on avoiding this workflow,
not a patch to WordPress core.

The private-network mu-plugin enforces `registration=none` and
`add_new_users=false` in Multisite only. Network Admin and WP-CLI direct user/site
creation remain available. Plugins can implement their own signup workflows, so
check those before enabling them.

When converting or importing an existing network, check for pending signups:

```bash
ddev wp db query "SELECT signup_id, user_login, registered FROM $(ddev wp db prefix)signups WHERE active = 0"
```

Run this from the host after conversion. Closing registration does **not**
invalidate previously issued activation links. Review and remove obsolete pending
signup records before relying on this exception; do not print activation keys.

If a derived project needs public registration, site-admin user registration, or
any custom signup/activation flow, reassess the advisory and this policy first.
Removing the mu-plugin or suppressing the audit does not fix plaintext key storage.
